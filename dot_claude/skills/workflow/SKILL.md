# 作業手順書（workflow）

`~/.claude/CLAUDE.md` の「進め方」が定める**重い判断**タスクは、この手順書に沿って計画してから着手する。自明・軽い判断のタスクはこの手順を踏まず着手してよい。

この手順書の中心は、成果を「完成形の一枚岩」でなく**人間がレビューできる単位の列**として届けることにある。粒度は3層で、役割が違う。

| 層 | 単位 | 役割 |
|---|---|---|
| PR | todo 内のグループ（見出し） | チームレビュー・マージ・停止（引き渡し）の単位 |
| todo 項目 | 段取り単位 | 計画・依存関係・中断再開 |
| スライス | 着手時に just-in-time 分割する子項目 | レビューログ・差分スナップショットの単位 |

設計承認ゲートと PR 境界での停止は、CLAUDE.md「確認すべき場面を絞る」の②（正解がユーザー側にしかない判断）に当たる明示的な確認点であり、「手を止めない」原則より優先する。

## 計画

1. **方針を決める**: いきなり書かない。既存コード・仕様を読む。着手前に `~/.agent/<cwd-slug>/`（「作業ファイル」節参照）を `ls`／Glob で一覧し、既存設計書・todo を確認して、関連する未完ゴールがあれば再開する。完了済みゴールの `.NN.patch` が残っていれば、このタイミングで削除する。
2. **設計書を書く（条件付き）**: 本質的な基準は「重い判断に当たるか（CLAUDE.md『進め方』参照）」。次のいずれかに当てはまり、かつ方針が自明でないなら作成する。
   - 方針に複数の選択肢があり、トレードオフ検討が必要（最重要・他はこれの代理指標）
   - 新規モジュール/パッケージの追加が必要
   - 既存インターフェース（API・DBスキーマ等）の変更が必要
   - 仕様書・要件定義が与えられており、規模・複雑さから事前の設計整理が要る

   いずれの条件に触れても、方針が一意に定まり検討の余地がなければ設計書は省く（「シンプル・最小限」を優先）。書く場合は目的・採用方針とその**理由**・不採用の代替案・主なリスクを書く。差分で分かる *what* より、後から追えない *why* を優先する。実装が設計と乖離したら、経緯と最終結論を追記して実態に合わせる。
3. **PR 分割計画を立てる**: ゴールを**独立にマージ可能な PR の列**に分割する（設計書を書く場合はその一部として書く）。各 PR はレビュー可能サイズに収める（判断を伴う差分でおおよそ 300〜400 行が目安）。分割の定石:
   - 準備リファクタリングは先行 PR に分離する
   - インターフェース定義と実装を分ける
   - リネーム追従・一括置換・生成コードなど機械的変更は単独 PR に隔離する
   - 未完成機能はフィーチャーフラグや未接続の状態でマージ可能にする

   PR を使わないプロジェクトでは「PR」を「レビュー区切り」と読み替えて同じ分割を行う（境界での停止・提示も同じ）。1 PR に収まる規模ならこの分割は不要。設計書を省く場合、この分割は todo の見出しグループとして表現する（「todo を書き出す」参照）。
4. **設計承認ゲート**: 設計書を書いた場合は、要点（採用方針とその理由・PR 分割）を提示し、**承認を得るまで実装に着手しない**。設計の是非と PR の切り方の両方にここで合意を取る（後から巨大 PR に直面させない）。設計書を省いた場合は、採る方針と PR 分割を一言提示してから着手してよい（停止は不要）。
5. **todo を書き出す（中断・再開や段取りが要るとき）**: 全体像・作業順序・依存関係を保存する（保存場所・命名は「作業ファイル」節）。PR 分割計画に従い、**PR 単位の見出しで項目をグループ化**する。各項目はひとまとまりの作業単位に分解する（「○○機能を実装」ではなく「モデル・マイグレーション」「ビジネスロジック」「テスト」）。短く一気に終わるなら todo ファイルは省いてよい。仕様書がある場合は全セクション・全項目を漏れなく展開し、展開後に再照合して抜け漏れを確認する。設計書を作らないゴールでも、判断理由・前提・想定外の発見が生じたら todo 内に書き残す。

## 実装

6. **todo に沿って実装する（着手時にスライス分割）**: 進捗の正本は常に todo ファイル。完了項目にチェックを付けて可視化する。項目に取りかかる時点で、変更が「1つの設計判断」を超えそうなら、項目の下に子項目（**スライス**）として分割してから実装する。スライスの基準:
   - **1スライス = 1つの設計判断**（またはそれを伴わない機械的変更のひとまとまり）。「このスライスで決めたことを一文で言えるか」が判定基準
   - 判断を伴うスライスは差分 ~150 行を目安とし、超えるなら判断が複数混ざっていないか疑う
   - 機械的変更は1スライスが大きくてよいが、**判断を伴う変更と同じスライスに混ぜない**（混ざるとレビュワーが全行を精読する羽目になる。レビュー負荷は行数でなく判断の数に比例させる）

   TaskCreate/TaskUpdate は「今のセッションで手を動かすスライス」を可視化したいときに todo ファイルから派生させる一時ビューであり、第2の記録ではない。セッション終了時は todo ファイルに反映し、TaskCreate 側は破棄してよい。設計書があれば照らし合わせ、乖離があれば立ち返る。
7. **スライスごとに記録する**: スライス（分割しなかった項目はその項目）を完了しチェックを付けるたびに、次の3つを行う。**コミットはしない**（git への書き込みは PR 境界のみ・ユーザー主導。「PR 境界で停止する」参照）。
   - **レビューログに1セクション追記**: 変更ファイル一覧（`file:line` 付き）、そのスライスでの設計判断、自信のない箇所・レビューしてほしい箇所。機械的変更なら「機械的・流し読み可」と明記する
   - **差分スナップショット**（git 管理下のみ）: `git diff HEAD` の出力を `~/.agent/<cwd-slug>/<YYYYMMDD>-<ゴール名>.NN.patch`（NN は 01 からの連番）に保存する。読み取り専用操作だけを使う。基準の HEAD が同じ間は累積差分になるため、同一 PR 内では連番の隣同士の差がそのままスライス単位の差分になる（PR 境界でユーザーがコミットすると基準が動くので、PR を跨ぐ比較には使わない）。新規（未追跡）ファイルは `git diff` に現れないため、レビューログの当該セクションに新規ファイルであることを明記して補う。git 管理外なら変更ファイルの列挙で代替する
   - **3行程度の中間報告**をチャットに流す: 何を変えたか・次に何をやるか
8. **PR 境界で停止する**: 1つの PR に属する項目がすべて終わったら、「完了前の検証」をその PR の範囲で行ったうえで**停止**し、次を提示する。
   - 該当スライスのレビューログと**読み順ガイド**（どの順で・何に注目して読むか）
   - PR description の下書き（レビューログを整形したもの。変更意図・読み順・注意箇所を含める）

   ブランチ作成・コミット・PR 作成は**ユーザー主導がデフォルト**。明示的に依頼されたときだけ実行し、実行後は `git log`・`gh pr view` で結果を必ず検証する。次の PR に進むのは指示を受けてから。マージ待ちを跨いで先行実装が必要なら stacked branch を提案する。ユーザーが「ゲート細かめで」等と指示したら、PR 境界でなくスライス単位で停止する（この場合の各停止はレビューログの提示のみでよく、「完了前の検証」は従来どおり PR 境界で行う）。
9. **問題が起きたらリプランする**: 突き進まず計画に戻り、方針を見直して todo を更新する。PR 分割が実態に合わなくなったら分割計画ごと見直し、変更をユーザーに伝える。
10. **中断時は todo を更新する**: 完了項目にチェックを付け、未完了項目と次の一手を明記してから中断する。次回 todo を読めば状況が分かる状態にする。

## 作業ファイル（設計書・todo・レビューログ）

特定タスクの計画・進捗・設計判断の置き場。プロジェクト固有の規約があればそれに従い、なければ以下に従う。

- **メモリ機構との住み分け**: 進行中タスクの手順・進捗・設計判断は `~/.agent` に置く。何をどちらに書くか（ハーネスのメモリ機構との住み分け）は CLAUDE.md「記憶と作業ファイル」が正本。
- **保存場所**: `~/.agent/<cwd-slug>/` 直下にフラットに置く。`<cwd-slug>` は作業ディレクトリの絶対パスの `/` を `-` に置換した文字列で、`pwd | sed 's#/#-#g'` で得られる（例: cwd が `/home/ubuntu/myproject` なら `-home-ubuntu-myproject`）。ディレクトリが無ければ初回書き込み時に `mkdir -p` で作成する。
- **ファイル名**: todo は `<YYYYMMDD>-<ゴール名>.todo.md`、設計書は `<YYYYMMDD>-<ゴール名>.design.md`、レビューログは `<YYYYMMDD>-<ゴール名>.review.md`、差分スナップショットは `<YYYYMMDD>-<ゴール名>.NN.patch`（`<YYYYMMDD>` は作業開始日）。日付＋ゴール名が共通なので同一ゴールの資料は隣接し、ファイル名順が時系列順になる。
- **1ファイル = 1ゴール**: 1つの todo には一貫した1ゴールだけを書く。ドメイン・目的の異なる作業（例: インフラ移行とアプリ個別設定）を束ねない。これで設計書との範囲のズレを防ぐ。同一ゴールの資料は**同じゴール名**でペアにし、種別はサフィックス（`.todo.md` / `.design.md` / `.review.md`）で区別する。
- **参照は相対リンク**: ファイル間の参照（todo→設計書など）は絶対パスでなく相対リンクにする。

## テスト

テストを書く/書かないの判断・実行確認の原則は CLAUDE.md「テスト・完了前の検証」が正本。本節はその粒度の補足。

- **粒度**: ドメインロジック・ビジネスルールは単体テスト、API/エンドポイントは統合テストで主要パスと異常系を検証する。UIの細かな表示テストは不要。

## 完了前の検証

完了前に必ず動作確認する原則は CLAUDE.md「テスト・完了前の検証」が正本。以下はその具体手順。**PR 境界ごとに、その PR の範囲で行う**（最後の PR ではゴール全体を突き合わせる）。

- **計画との突き合わせ**: todo・設計書・仕様書があれば全項目が実装されているか突き合わせる。設計書が実態と一致しているか、レビューログに全スライスが載っているかも確認する。未実装があれば実装に戻る。
- **動作確認**: 作業種別に応じた成果の確認を実際に行う。アプリ実装ならビルドが通る・起動する・マイグレーションが正常実行できる等。インフラ・設定なら適用・反映の確認、ドキュメント・調査なら成果物が要件を満たすかの確認。
- **差分確認**: git管理下ならベースブランチ（main 等）との diff を確認し、意図しない変更が混ざっていないか確かめる。git管理外なら、変更・新規作成したファイルを列挙し、意図しないファイルに触れていないか目視確認する。
- **テスト実行**: 関連テストを実行し全てパスを確認する。
- **自己レビュー**: 不要なデバッグコード・コメント・TODO が残っていないか確認する。
- **後始末**: `.NN.patch` はユーザーがレビューに使う可能性があるためゴール完了時点では消さず、次のゴールの着手時に削除する（「計画」1）。設計書・todo・レビューログは経緯の記録として残す。
