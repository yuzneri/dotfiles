以下の対象の仕様を策定し、仕様書ファイルに残してください。

## 対象
$ARGUMENTS

引数は以下のように解釈する。

- 作りたいもの・解決したい課題の説明 → 新規に仕様を策定する
- 既存の仕様ファイルのパス（`*.spec.md`）→ その仕様を更新する（「更新モード」参照）
- 資料のパス／URL（要望メモ・issue・議事録・既存ドキュメント等）→ 読み込んで出発点にする
- 引数がない場合 → 作業ファイル置き場の既存仕様書を一覧し、未完のものがあれば再開の可否をユーザーに確認する。なければ対象を確認する

## このスキルの範囲

**what（何を作るか）を確定させる。how（どう実装するか）は書かない。**

- 仕様書に書くのは、目的・利用者・スコープ・振る舞い・制約・受け入れ条件。実装非依存の言葉で書く
- 実装方針・アーキテクチャ・モジュール構成・PR 分割は `/workflow` の設計書（`.design.md`）の担当。仕様書はその入力になる（「/workflow との関係」参照）
- 実装の都合が仕様を縛る場合（既存 DB スキーマ、外部 API のレート制限、動作環境など）は「制約・前提」に what の言葉で書く。「◯◯ライブラリを使う」のような手段の選択は書かない
- 実装予定のない仕様（アイデア段階の機能仕様、外部に説明するための仕様）も対象とする。この場合も仕様書単体で読んで完結する状態にする

## 手順

1. 状況を把握する
2. 論点を洗い出す
3. 対話で詰める
4. 仕様書を書く
5. 報告する

### 1. 状況を把握する

**質問の前に、自分で調べれば分かることを調べ切る**（CLAUDE.md「事実から始める」）。ユーザーの時間を、ユーザーにしか答えられない判断に使う。

- 作業ファイル置き場（「仕様書ファイル」節）を一覧し、既存の仕様書・設計書・todo を確認する。関連するゴールがあれば新規作成でなく更新にする
- 対象プロジェクトの既存実装・README・設定・既存の仕様ドキュメントを調べ、現状と制約を把握する。調査はサブエージェントに委譲する（CLAUDE.md「調査・サブエージェント」）
- 引数で資料が与えられていれば読む。URL は WebFetch、PDF/Office は MarkItDown を使う
- 外部の仕様・標準・ライブラリの制約に依存する部分は一次情報で裏を取る（Context7・MDN 等）

### 2. 論点を洗い出す

以下の観点で、仕様が未確定な点を列挙する。全観点を機械的に埋めようとしない。対象に関係する観点だけを扱う。

- **目的**: どんな課題を解決するか。解決したと言える状態は何か
- **利用者と利用シーン**: 誰が、どんな状況で、何のために使うか
- **スコープ**: やること／やらないこと。特に「やらないこと」を明示する（後から膨らむのを防ぐ）
- **入出力**: 何を受け取り、何を返すか。データの形式・単位・精度・必須／任意
- **振る舞い**: 主要フロー。状態を持つなら状態と遷移条件。副作用（永続化・通知・外部送信）
- **異常系・境界条件**: 空・0件・上限超過・重複・同時実行・依存先の失敗をどう扱うか。何をエラーとし、何を許容するか
- **制約・前提**: 性能・データ量・互換性・セキュリティ・権限・運用上の前提
- **受け入れ条件**: 何が満たされたら完成か。検証可能な形で書けるか

洗い出した論点を3つに仕分ける。

1. **調べれば分かる** → 調べる。質問に回さない
2. **妥当な既定値を置ける** → 仮案を立てる。仕様書に「既定値として置いた」と明記する
3. **ユーザーにしか答えがない**（スコープの取捨、優先順位、トレードオフの選好、外部事情） → 質問に回す

### 3. 対話で詰める

- **AskUserQuestion でまとめて出す**。1問1答の往復にしない
- **オープンな質問をしない**。仮案・選択肢・トレードオフを提示して選んでもらう形にする。「エラー時はどうしますか？」ではなく「①3回リトライして諦める ②即座に失敗を返す ③キューに退避して後で再処理。既定は①、理由は〜」
- **重要な論点から聞く**。決まると他が連鎖して決まるもの、後から覆すと手戻りが大きいものを先に出す
- **ラウンドは2〜3回を目安にする**。回答で新たな論点が生じたら次のラウンドに回す。枝葉は既定値で埋め、仕様書に既定値である旨を書く。質問を無限に続けない
- **矛盾・実現困難・過剰スコープはその場で指摘する**（CLAUDE.md「率直に指摘する」）。指摘したうえでユーザーが同じ判断をしたら、それを採用し、判断と理由を「決定の記録」に残す
- **決まらない論点は未決事項にする**。決着しないものを無理に決めさせず、未決のまま仕様書に書いて対話を打ち切る

### 4. 仕様書を書く

「記述規範」に従い、「仕様書ファイル」の場所・命名・構成で書き出す。

### 5. 報告する

「報告フォーマット」に従う。

## 記述規範

- **検証可能に書く**: 「高速に応答する」ではなく「95パーセンタイルで200ms以内」、「大量のデータ」ではなく「1リクエストあたり最大10万件」。受け入れ条件は、それを見てテストが書ける粒度にする
- **曖昧語を使わない**: 「適切に」「必要に応じて」「柔軟に」「等」は、何も決めていないことを決めたように見せる。具体を書くか、未決事項に落とす
- **決めていないことを決めたように書かない**: 推測で埋めない。分からないものは未決事項に書く（CLAUDE.md「分からないことは分からないと言う」）
- **非自明な仕様には理由を添える**: なぜその値・その挙動なのかは、後から仕様書を読む人には復元できない。why を1行添える
- **実装の詳細を書かない**: クラス名・関数名・ライブラリ選定・内部データ構造は書かない。それらは設計書の担当
- **網羅より正確さ**: 埋まらない項目は見出しごと省く。空欄を埋めるための創作をしない

## 仕様書ファイル

- **保存場所**: `~/.local/state/agents/<project-slug>/` 直下（`<project-slug>` の定義は CLAUDE.md「記憶と作業ファイル」が正本。保存場所と `<YYYYMMDD>-<ゴール名>` の命名パターンは workflow スキルの「作業ファイル」と共通で、`.spec.md` が本スキル固有の種別）。ディレクトリが無ければ `mkdir -p` で作成する
- **ファイル名**: `<YYYYMMDD>-<ゴール名>.spec.md`。同一ゴールの設計書・todo が既にあれば**ゴール名を揃える**（ファイル名順で隣接し、関連資料がまとまる）
- **1ファイル = 1ゴール**: 目的の異なる仕様を1ファイルに束ねない
- **参照は相対リンク**: 他の作業ファイルへの参照は相対リンクにする
- **リポジトリに残したい場合**: プロジェクトに仕様書の置き場（`docs/` 等）の規約があるならそちらに置く。その場合も本スキルの構成・記述規範は同じ

### 構成

対象に合わせて見出しを取捨する。埋まらない見出しは省く。

- **概要**: 何を作るかを3文以内で
- **目的・背景**: 解決する課題と、解決したと言える状態
- **利用者と利用シーン**
- **スコープ**: やること／やらないこと
- **用語**: プロジェクト固有の語の定義（曖昧さの温床になる語だけ）
- **機能仕様**: 機能ごとに、入出力・振る舞い・異常系・境界条件
- **制約・前提**: 性能・互換性・セキュリティ・運用・外部依存
- **受け入れ条件**: チェックリスト形式
- **未決事項**: 決まっていない論点と、決めるために必要な情報・判断者
- **決定の記録**: 対話で決めた重要な判断について「決めたこと／理由／不採用にした案」。仕様本文の why では足りない、経緯を残すべき判断だけを書く

### 更新モード

既存の `.spec.md` を対象にした場合。

- 既存の仕様を読んでから対話に入る。既に決まっていることを聞き直さない
- 本文は最新の仕様に書き換える（旧仕様をコメントアウトや併記で残さない）
- 変更が既存の決定を覆す場合は「決定の記録」に追記する（何を、なぜ変えたか。以前の判断も残す）
- 未決事項が解決したら未決事項から削除し、本文に反映する

## /workflow との関係

- 実装に進む場合、この仕様書が `/workflow`「計画」の言う**仕様書**になる。`/workflow` はこれを読んで設計書（`.design.md`）と todo を起こす
- **仕様書は what、設計書は how**。実装方針・トレードオフ・PR 分割は設計書に書き、仕様書に混ぜない
- 実装着手は `/workflow` の担当。本スキルは仕様書を書き終えた時点で止まる
- **実装中に仕様が変わったら仕様書を更新する**（`/spec <仕様書パス>`）。仕様変更を設計書やレビューログに書き溜めない。仕様書が what の正本であり続ける状態を保つ

## 報告フォーマット

チャットには要点だけを報告する。仕様の全文を貼らない。

### 仕様の要点
何を作るかを5〜10行で。スコープの「やらないこと」も含める。

### 決めた重要な判断
対話で決めた判断のうち、影響の大きいものを理由付きで3点程度。

### 未決事項
残っている論点と、決めるために必要なもの（なければ「なし」）。

### ファイル
仕様書のパス。更新モードなら変更した箇所の要約も。

### 次の一手
実装に進むなら `/workflow` で設計・計画に入れることを案内する。仕様の追記・修正が必要なら `/spec <パス>` で更新できることを案内する。
